## 一、项目定位与目标

### 1.1 一句话定位

一个以**知识点掌握度**为状态中枢的学情驱动自适应学习闭环系统。通过学生端、老师端、教研组长端三个 Agent，打通"布置作业 → 引导式作答 → 人机协同批改 → 错题归因 → BKT 掌握度更新 → 学情分析 → 反向指导组卷"的完整数据链路。

系统名字的含义：三端看到的不是三套系统，是同一份掌握度数据的三个切面。

### 1.2 本项目的双重目标

| 目标类型 | 具体目标                                                                                         |
| ---- | -------------------------------------------------------------------------------------------- |
| 业务目标 | 交付一个教育行业真实可用、业务闭环完整的 MVP 产品原型                                                                |
| 技术目标 | 在工程实践中落地主流 AI Agent 技术栈：LangChain、LangGraph、CrewAI、FastAPI、Neo4j、Milvus、RAG，并落地教育领域的经典算法 BKT |

## 二、用户角色与权限

**角色分配原则（v1.5 定稿）**：**不做自主注册**。账号由管理员通过 CSV 导入或管理后台创建，角色在创建时指定，用户永远无权决定自己的角色。二期如需开放注册，走角色邀请码（`STU-` / `TCH-` 前缀定角色）。

| 角色   | 权限边界                                                | 本版实现方式                                                                 |
| ---- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| 学生   | 只能看自己的作业、作答记录、掌握度                                   | JWT `roles` 含 student，查询按 student_id 过滤                                |
| 科任老师 | 只能看自己任教班级的数据                                        | JWT `roles` 含 teacher，数据范围来自 `teaching_assignments`（teacher ↔ 班级 ↔ 学科） |
| 教研组长 | 可看全年级跨班级数据（仅聚合，无学生明细）                               | JWT `roles` 含 researcher，任命记录在 `research_leads`（user ↔ 年级 ↔ 学科）        |
| 管理员  | **最小管理后台（见 2.2）**：用户与授课关系维护、CSV 导入；题库与演示数据仍走 CLI 脚本 | JWT `roles` 含 admin                                                    |

**一人多角色（v1.5 定稿）**：现实里教研组长往往也带课，`users` 表不存 role 字段，改 `user_roles` 多对多表（见 2.3）。JWT 签发 `roles: ["teacher", "researcher"]` 数组。

**教研组的定义（v1.5 定稿）**：**教研组不是一个实体表，它是"年级 × 学科"这个二维坐标**。"初二数学教研组" = 所有教初二数学的老师（来自 `teaching_assignments`），组长由 `research_leads` 任命产生。不单独建 `research_groups` 表，避免与排课数据冗余打架。

**RAG 权限隔离**：教材知识库三端可见；题库、教学参考资料仅老师和教研角色可见。向量库按 collection 物理隔离 + 检索时按 role 二次过滤，学生检索不到教师资源。

### 2.2 管理员能力：最小管理后台 + CLI 脚本并存

**A-01 最小管理后台**（v1.5 新增，约 2~2.5 天）：纯 CRUD 界面仍然不做，但**用户与授课关系是全部权限隔离的数据源**，学校管理员不可能跑命令行，这两块必须给界面。范围锁定 6 项，超出即砍：

| # | 功能            | 说明                                                                         | 优先级 |
| - | ------------- | -------------------------------------------------------------------------- | --- |
| 1 | 用户 CSV 批量导入   | 模板下载 + 上传 + **逐行校验、全过才写库**，返回导入报告（成功 N / 失败 M 及行号原因）                       | P0  |
| 2 | 用户单条增删改查 + 停用 | 转学、换班、离职是常态；停用（is_active）而非物理删除，保住历史作答数据                                   | P0  |
| 3 | 授课关系维护        | teacher ↔ 班级 ↔ 学科（teaching_assignments）增删改，**scope 数据源**                   | P0  |
| 4 | 教研组长任命        | user ↔ 年级 ↔ 学科（research_leads）；勾选 researcher 角色时强制先填任命，否则空 scope 登录即处处 403 | P0  |
| 5 | 班级管理          | 年级 / 班名 / 班主任，建用户前得先有班级                                                    | P1  |
| 6 | 操作日志查看        | audit_logs 查询页，谁导入/改了什么可追溯                                                 | P1  |

### 2.3 权限模型细则：双通道 scope（v1.5 新增）

隔离的本质是**查询时强制注入数据范围，而不是前端藏按钮**。多角色的数据范围是**两条独立通道，永不融合**：

| 通道             | 角色来源                   | 数据范围                         | 可见                            | 不可见                  |
| -------------- | ---------------------- | ---------------------------- | ----------------------------- | -------------------- |
| detail 明细通道    | `teaching_assignments` | 自己任教的 (class_id, subject) 集合 | 任教班级学生作答明细、批改、T-03            | 别的班、别的学科             |
| aggregate 聚合通道 | `research_leads`       | (grade, subject)             | 全年级该学科聚合：班级对比、年级掌握度、R-04、R-08 | **任何学生明细（接口层面就不提供）** |

实现要点（代码骨架见架构文档 8.4）：

```python
def get_scopes(user) -> list[dict]:
    scopes = []
    if "teacher" in user.roles:
        scopes.append({"type": "detail", "class_ids": [...], "subject": user.subject})
    if "researcher" in user.roles:
        scopes.append({"type": "aggregate", "grade": user.grade, "subject": user.subject})
    if "student" in user.roles:
        scopes.append({"type": "self", "student_id": user.id})
    return scopes
```

**关键禁令：千万不要把两个 scope 融合成"初二数学所有班级明细"**——那会让组长意外获得全年级学生明细查看权，比不隔离还糟。明细接口只认 `detail`，聚合接口只认 `aggregate`，各取所需。

### 2.4 安全基线（v1.6 新增：4 项现在做 + 3 项生产化做）

教育场景面向未成年人，安全合规是红线。按"现在做"与"生产化做"拆开，避免混在一起吃掉排期：

| 项 | 时机 | 做法 |
|---|---|---|
| 越权测试矩阵 | **现在做**（10.22，约半天） | 每接口 × 每角色全组合：researcher 调学生明细 403、student 调 teacher 接口 403、非 admin 调 admin 403 等，全部进 `test_scope_isolation.py` |
| 密码强度策略 + 失败锁定 | **现在做**（10.14，随 auth） | passlib bcrypt 加盐；弱密码拒绝；连续 5 次失败锁 15 分钟 |
| 内容安全简版过滤 | **现在做**（10.17，Agent 入口） | 学生对话节点入口过一层：system prompt 硬约束 + 关键词黑名单兜底；完整审核服务放生产化 |
| 敏感操作审计 | **现在做**（10.18） | 授课关系变更、批改确认、admin 导入等写 audit_logs（表已建，中途埋点） |
| JWT refresh token | 生产化 | 一周版缩短 access token 有效期 + 登出作废即可 |
| HTTPS | 部署阶段 | 内网演示可 HTTP；接入学校网络前必须（自签或内网 CA） |
| 未成年人合规文书 | 生产化 | 监护人知情同意、数据保留期限、删除机制；本地化部署已规避出境问题 |

## 三、MVP 核心闭环

### 3.0 三大主场景（S / T / R 主链路总览）

> 本节是三大端主场景的时间线总览，各场景的详细功能点见第四章对应小节。

**场景 A · 学生端：引导式作业练习（S-04 主链路）**

```
老师布置作业(T-01) → 分发至所带班级
学生进入作答会话(S-04) → 输入先过安全校验与意图分类（五类：要答案/要引导/提交作答/要讲解/闲聊）
按意图路由 → 引导（只搭脚手架，不给答案） / 讲解（RAG 检索教材与图谱） / 提交判分 / 闲聊接话引回
作答判分 → 错因归因（仅答错，4 类结构化输出） → BKT 掌握度更新 → 写回 bkt_state
```

一句话：学生每一次作答（无论走哪条分支）都实时沉淀为知识点掌握度。

**场景 B · 教师端：作业组卷与批改（T 系主链路）**

```
老师定义配额（知识点 × 题数 × 分值） → 系统配额抽题(select_questions_by_quota，错题沉底 / 近 7 天去重)
学生提交 → 客观题规则直判（交卷即得） → 主观题 LLM 建议 + HITL 确认（采纳 / 改分）或完全手动
commit_grade 同事务落库（批改记录 / 作答回填 / 审计留痕） → 同步更新 BKT 掌握度
作答与完成度汇总(homework_submissions) → 供班级学情查询
```

一句话：客观题零人工，主观题 AI 提效但教师终审——批改结论既进学情又反哺掌握度。

**场景 C · 教研端：学情分析与组卷闭环（R 系主链路）**

```
学情查询（年级 / 班级） → 数据源：bkt_state 知识点掌握度
薄弱知识点驱动组卷(exam_crew) → 教研人工审核定稿 → 按年级推送
考试作答 → 批改回流(exam_attempts 总分) → analysis_crew 考后分析（数据源：考试作答记录）
分析结论回流 → 题库质量更新 + 驱动下一次组卷 → 教学闭环
```

一句话：学情与组卷以掌握度为主线，考后分析以考试作答为源，分析结果回流形成闭环。

### 3.1 全局数据流图

```
老师布置作业 (T-01)
    ↓ 按知识点抽题生成作业，题目关联 knowledge_point_id
学生引导式作答 (S-04)
    ↓ LangGraph Agent 不给答案，走"提示→再试"多轮引导，attempt_count 递增
自动批改 (T-02)
    ↓ 客观题规则直判即生效；主观题 LLM 出建议，interrupt 挂起等老师确认
错题归因 (S-05)
    ↓ LLM 结构化输出 4 类错因，定位知识点，Neo4j 追溯前置薄弱点，推同类题
BKT 掌握度更新 (C-01)
    ↓ 贝叶斯更新 P(known)，错因调节 slip 参与更新，叠加遗忘衰减，双写 PostgreSQL + Neo4j
班级错题汇总 (T-03)  →  年级掌握度 (R-01)  →  试卷分析 (R-04, CrewAI)
    ↓
┌─────────── 分析结果的两条反向通路（v1.2 新增）───────────┐
│  ① 学生侧：错题库 + 图谱 → 诊断测验生成 (S-10) → 回到 S-04 作答   │
│  ② 教研侧：掌握度 + 历史异常题 → 试卷生成 (R-08) → 考试 → 回到 R-04 │
└──────────────────────────────────────────────────┘
```

**双闭环说明**：一期只有"作业"这一条单向主链路，分析结果没有反向出口。加入 S-10 与 R-08 后形成两个次级闭环——学生的错题自动生成补救测验，教研的分析结论自动生成下一阶段的卷子，考完之后的数据又回流给 R-04 分析。这也让全局数据流真正闭合到 T-01 的组卷环节。

**上线判定**：上述链路数据全通，三端界面能看到彼此产生的数据。

## 五、核心算法规格

### 5.1 掌握度模型：BKT 贝叶斯知识追踪

**选型理由**：每个知识点只需 4 个参数，是 K12 智能辅导系统的经典标配模型。相比自研加权公式，它可解释、经得起追问，且不需要预先训练数据。

**四个参数**（先使用领域常用默认值，数据积累后再用 EM 算法拟合）：

| 参数      | 含义             | 默认值  | 调节建议              |
| ------- | -------------- | ---- | ----------------- |
| p_init  | 初始掌握概率（先验）     | 0.10 | 全区统一初值            |
| p_learn | 一次练习后由不会转为会的概率 | 0.30 | 难点调低，易错易会的可调高     |
| p_slip  | 会但做错的概率（失误）    | 0.10 | 由错因动态调节，见下表       |
| p_guess | 不会但蒙对的概率       | 0.20 | 选择题偏高，解答题调低至 0.05 |

**更新三步走**，设 P 为学生在该知识点上的掌握概率：

第一步，遗忘衰减（距上次作答 Δt 天）：

```
P ← P × exp(-λ × Δt)      λ = ln2 / 7 ≈ 0.0990（半衰期 7 天）
```

第二步，贝叶斯后验修正（obs = 1 答对，obs = 0 答错）：

```
答对：P ← P·(1 - p_slip) / [P·(1 - p_slip) + (1 - P)·p_guess]
答错：P ← P·p_slip       / [P·p_slip       + (1 - P)·(1 - p_guess)]
```

第三步，叠加学习效应（练一次本身就会提升）：

```
P ← P + (1 - P) × p_learn
```

**与错因归因的联动**（本设计的关键点）：错因不直接改写掌握度数值，只通过调节本次的 p_slip 参与贝叶斯更新，避免同一个数字被两套规则同时修改而失控。

| 错因   | 本次 p_slip | 含义                  |
| ---- | --------- | ------------------- |
| 概念不清 | 0.05      | 确实没掌握，几乎不留余地地压低 P   |
| 方法不会 | 0.10      | 默认值，正常走未掌握路径        |
| 粗心   | 0.45      | 视为"会但算错"，P 下降幅度明显放缓 |
| 审题失误 | 0.35      | 不因读错题就重判为完全不会       |

**掌握度分级与系统行为**：

| 掌握度区间       | 等级   | 系统行为         |
| ----------- | ---- | ------------ |
| ≥ 0.85      | 掌握   | 不重复推题        |
| 0.60 ~ 0.85 | 基本掌握 | 少量巩固练习       |
| 0.40 ~ 0.60 | 薄弱   | 主动推同类题       |
| < 0.40      | 严重薄弱 | 触发预警，追溯前置知识点 |

**落地形态**：

- 新增 `bkt_state` 表：`student_id`、`kp_id`、`p_known`、`last_updated`
- 核心函数 `update_mastery(student_id, kp_id, is_correct, error_type)`，纯 Python 二三十行
- 每次更新双写：PostgreSQL `mastery_records`（时序快照）+ Neo4j `MASTERY` 关系属性
- 验收方式：构造固定作答序列（连答对 / 连答错 / 答错但错因粗心），验证 P 的变化方向与幅度符合预期

### 5.2 错因归因（结构化输出）

四大错因类别与判定依据：

| 错因   | 判定要点               | BKT 联动方式（详见 5.1）     |
| ---- | ------------------ | -------------------- |
| 概念不清 | 公式/定义用错，对知识点本身理解有误 | slip=0.05，判定为真没掌握    |
| 方法不会 | 知道考什么，但解题路径没建立起来   | slip=0.10，走默认未掌握路径   |
| 粗心   | 计算错误、抄写错误，思路正确     | slip=0.45，P 下降幅度明显放缓 |
| 审题失误 | 漏条件、会错题意，答非所问      | slip=0.35，不因读错题重判为不会 |

输出结构：

```python
class ErrorAttribution(BaseModel):
    error_type: Literal["概念不清", "粗心", "方法不会", "审题失误"]
    confidence: float          # 0~1 置信度
    evidence: str              # 归因依据，须引用学生作答的具体片段
    knowledge_point: str       # 定位到的知识点 id
    explanation_strategy: str  # 讲解策略：重讲概念 / 梳理解题步骤 / 提醒检查 / 训练审题
```

### 5.3 组卷引擎（三种模式共用）

本版有三处需要组卷，共用一个底层引擎 `select_questions(kp_weights, difficulty_plan, exclude_ids)`，**保证三处行为一致、可单测**：

| 调用方       | 场景           | 知识点来源          | 难度策略                     |
| --------- | ------------ | -------------- | ------------------------ |
| T-01 布置作业 | 随堂/课后作业      | 老师手工勾选的知识点     | 老师指定单档（easy/medium/hard） |
| S-10 诊断测验 | 学生个人补救练习     | 个人错题库 + 图谱前置链  | 与掌握度反相关自动定档              |
| R-08 试卷生成 | 月考 / 期中 / 期末 | 年级错题热点 或 全章节覆盖 | 按配额表分档配题                 |

**引擎通用流程**：

```
1. 按 knowledge_point_id 从题库筛候选题（含难度、题型、quality_flag 字段）
2. 按难度分档过滤；命中 quality_flag = 'abnormal' 的题目降权 50%，'disabled' 直接剔除
3. 排除该班级近 7 天已布置过的题目（exclude_ids 由 homework_history 查出）
4. 单知识点超额（>2 题）时截断，把配额让给次优先知识点
5. 题量不足时放宽到相邻难度档补齐；仍不足则记录缺口，宁可少题不乱补
```

> 关键工程原则：**选题是确定性计算，不交给 LLM**。LLM 只负责决定"选哪些知识点、各占多少比重"（配额表），真正抽题由 Python 规则执行——与 R-04「Pandas 算指标、LLM 只解读」是同一套设计哲学：该确定的部分绝不外包给模型，保证结果可复现、老师可信任。

### 5.4 诊断测验生成（S-10）

**四步算法**：

```
Step 1  取错题：errors = 该学生近 30 天 error_logs，去重得错题知识点集合 E
Step 2  图谱外扩：对 E 中每个节点走 1~2 跳前置边 HAS_PREREQUISITE，得候选集 C = E ∪ P
        MATCH (e:KnowledgePoint)<-[:HAS_PREREQUISITE*1..2]-(p:KnowledgePoint)
        WHERE e.id IN $E RETURN DISTINCT p.id
Step 3  排序取点：按该学生 BKT 掌握度 p_known 升序排，取 Top-5 作为目标知识点
        （同掌握度时按错题频次降序，保证"又弱又常错"的优先）
Step 4  逐点配题：每点抽 1~2 题，难度由掌握度反相关映射，总量 8 题
        p_known < 0.40 → easy（先补地基）
        0.40 ~ 0.70   → medium
        > 0.70        → hard（少量，验证是否能迁移）
```

**输出结构**（给前端渲染测验卡片）：

```python
class DiagnosticQuiz(BaseModel):
    student_id: str
    target_points: list[TargetPoint]   # 每个元素含 kp_id / kp_name / p_known / reason
    questions: list[QuizQuestion]      # 8 题，含 kp_id、difficulty、source（是原题所属，还是前置点）
    total_count: int
    generated_reason: str              # 面向学生的一句话："你最近在 xxx 上连错了 3 次"
```

**与 S-05 的边界**：S-05 是单题归因后"顺手推 1 道同类题"，属于即时反馈；S-10 是一次性横向铺开多知识点、带优先级排序和配额定档的系统性补救测验。两者共用 `search_question_bank` tool，但 S-10 多走了一遍图谱前置追溯。

### 5.5 试卷生成（R-08）

**两种模式的配额差异**：

| 维度      | 月考（巩固型）                             | 期中 / 期末（摸底型）             |
| ------- | ----------------------------------- | ------------------------ |
| 目标      | 纠正阶段性共性错误                           | 全面摸底阶段学习成果               |
| 知识点来源   | 年级错题 Top10 知识点 + 其前置链路，**占比 ≥ 70%** | 按章节均匀覆盖，**章节覆盖率 ≥ 80%**  |
| 难度分布    | 易 40% / 中 45% / 难 15%               | 易 70% / 中 20% / 难 10%    |
| 题型要求    | 不做强制约束                              | 选择 : 填空 : 解答 ≈ 4 : 3 : 3 |
| 异常处理    | 避开历史 P<0.3 的偏难题                     | 保留区分度好的题，剔除历史 D<0.2 的无效题 |
| 总分 / 题量 | 100 分 / 20 题（默认，可配置）                | 100 分 / 25 题（默认，可配置）     |

**CrewAI 三角色编排**（`exam_crew`，与 `analysis_crew` 并列）：

```
① 命题规划师 (Planner)
   输入：考试类型 + 年级掌握度 + 错题热点 + 历史异常题清单
   输出：Pydantic 结构化配额表 QuotaPlan = [{kp_id, question_count, difficulty, reason}, ...]
   ★ LLM 只出到这一层，配额表可打印、可人工改

② 选题执行器 (Selector)
   输入：QuotaPlan
   动作：抽题逻辑全在 select_questions_by_quota 这个 tool 里（纯 Python 规则），
        Agent 本身配低温模型且被禁止自行出题，只负责把手上的配额翻译为工具调用
   输出：PaperDraft + 缺口清单（哪些知识点题量不够）

③ 质量审核员 (Reviewer)
   输入：PaperDraft + 覆盖率/难度/重复率三项硬指标
   动作：三项指标用 Python 算，不过关则由 LLM 给出修正意见回传给 ② 重试，最多 2 轮
   输出：通过则落地为一 exams 记录，可选调用 LLM 生成卷首话术
```

**与 R-04 的考后闭环**：R-04 分析出的异常题（P / D 越界）会写回 `questions.quality_flag`，R-08 下次命题时自动降权或剔除。这条"考后分析 → 考前改进"的回流是整个设计里最有价值的一环，也把原来的单向链路彻底闭合成环。

### 5.6 试卷分析指标（R-04）

| 指标     | 公式                                       | 异常阈值                  |
| ------ | ---------------------------------------- | --------------------- |
| 得分率 R  | 该题平均得分 / 该题满分                            | 无                     |
| 难度系数 P | P = 平均得分 / 满分（值越大越简单）                    | P < 0.3 过难，P > 0.9 过易 |
| 区分度 D  | D =（前 27% 高分组平均得分 - 后 27% 低分组平均得分）/ 该题满分 | D < 0.2 区分度不足         |

**异常题判定**：P < 0.3 或 P > 0.9 或 D < 0.2，命中任一即标注，交由 CrewAI 解读成因。

## 八、风险与边界

| 风险                           | 影响                     | 应对方案                                                                           |
| ---------------------------- | ---------------------- | ------------------------------------------------------------------------------ |
| CrewAI 调试耗时超预期               | D5 阻塞                  | 开发前先跑通一个 CrewAI 最小示例确认环境可用；仍不通则改为单个 LangGraph 调用，保住闭环                          |
| BKT 参数取值不当导致掌握度失真            | 全链路数字不可信               | 先用领域默认值（0.1/0.3/0.1/0.2），构造固定作答序列单测验证方向与幅度，不随意调参                               |
| interrupt resume 与 SSE 配合复杂  | D6 阻塞                  | 降级方案：主观题确认改为同步 POST 接口，不做流式                                                    |
| 题库数据量不足，分析没意义                | 演示效果差                  | 保证至少 150 道题覆盖 10 个知识点，用脚本合成作答记录                                                |
| Neo4j 环境起不来                  | 全链路阻塞                  | D1 上午必须验证 Neo4j 连通性，否则改用 PG 邻接表                                            |
| 两个 CrewAI crew 一起调，依赖冲突或耗时翻倍 | D5 阻塞                  | 先跑通一个最小 crew 示例再写业务；`analysis_crew` 与 `exam_crew` 共用 tool 层，不重复配置              |
| S-10 图谱前置外扩把题目池撑得过大          | 测验不聚焦                  | 前置只走 1~2 跳，最终只用掌握度 Top5 知识点配题，不把整个候选集都拿来选题                                     |
| R-08 出卷后无人作答，演示看不出闭环         | 演示断层                   | 用脚本对虚拟班级批量"作答"生成成绩，直接喂给 R-04 分析，展示"出卷 → 考试 → 分析"整段                             |
| Milvus 环境起不来或维度配错            | D2 阻塞                  | D1 就把容器起了并建好空 collection（dim=1024）；真起不来则临时降级为内存向量检索，保住 RAG 链路可演示               |
| PostgresSaver 忘调 setup()           | 首次写 checkpoint 报关系不存在         | 应用启动时幂等调用一次 `checkpointer.setup()`（v1.6 已持久化，重启不再丢会话） |
| 管理后台挤压核心闭环开发时间               | 闭环做浅                   | 10.21 集中一天做，按 6 项优先级砍尾（先砍日志页、班级页）；P0 三项不可砍，它们是权限模型的地面                          |
| 多角色 scope 被错误融合              | 组长意外获得全年级学生明细，越权比不隔离还糟 | 明细/聚合两条通道独立返回、独立消费，禁止合并；写一条"researcher 无法调学生明细接口"的越权单测                         |
| 勾了 researcher 未填任命           | 空 scope，登录处处 403 难排查   | 管理后台勾选 researcher 时强制先填 research_leads（年级+学科），保存前校验                            |
| InMemoryStore 误当持久化长期记忆      | 重启后学生画像丢失              | 明确它是"跨 thread 不跨进程"；用 PostgreSQL 当真源 + Store 当缓存 + 进节点前幂等预热兜底（详见架构文档 4.4），本项为可选加分项 |
